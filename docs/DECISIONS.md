# บันทึกการตัดสินใจทางเทคนิค (Decisions Log)

เอกสารบันทึกเหตุผลและการตัดสินใจเชิงสถาปัตยกรรมของโปรเจกต์ **Life Cycle**

---

### 1. การตั้งชื่อแอปพลิเคชัน
- **การตัดสินใจ**: กำหนดชื่อทางการของแอปพลิเคชันเป็น **Life Cycle** แทนชื่อชั่วคราวเดิม (LifePlan)
- **เหตุผล**: ตามข้อกำหนดของระบบ โดยปรับปรุงในส่วนของเอกสาร หน้า UI ไตเติลเว็บ และเมตาแท็กทั้งหมด

### 2. นโยบายห้ามใช้ Emoji (Strict No-Emoji Policy)
- **การตัดสินใจ**: หลีกเลี่ยงและลบ Emoji ทั้งหมดออกจากระบบ โดยติดตั้งฟังก์ชัน `removeEmojis()` ใน `backend/src/lib/sanitize.ts`
- **เหตุผล**: ป้องกันความไม่สม่ำเสมอในการแสดงผลบนระบบปฏิบัติการต่างๆ และตรงตามข้อกำหนดของงาน

### 3. การคำนวณโภชนาการแบบ Deterministic
- **การตัดสินใจ**: ตัวเลข BMR, TDEE, แคลอรี่เป้าหมายคำนวณด้วยโค้ดผ่านสูตร Mifflin-St Jeor เสมอ โดยไม่ปล่อยให้ AI คิดตัวเลขเอง
- **เหตุผล**: เพื่อความถูกต้องทางโภชนาการ ความปลอดภัยต่อสุขภาพของผู้ใช้ และลดความแปรปรวนของคำตอบจาก AI

### 4. การจัดการแผน 30 วันและการจัดสรรตารางเวลา
- **การตัดสินใจ**: ให้ AI / Template สรุปแผนหลัก 7 วัน แล้วใช้ฟังก์ชัน `expandWeekTo30Days()` ขยายเป็น 30 วัน พร้อมฟังก์ชัน `generateDailySchedule()` จัดตารางเวลารายวันตามเวลาว่างและมื้ออาหารของผู้ใช้
- **เหตุผล**: ลดจำนวน Output Token จากการเรียก AI ช่วยให้ระบบตอบสนองรวดเร็ว ป้องกันข้อผิดพลาดด้านการจัดสรรเวลา และสามารถปรับเพิ่มความหนัก (Progression) และสัปดาห์พักฟื้น (Deload) ได้อย่างเป็นระบบ

### 5. การจัดการสิทธิ์และการหมดอายุของ Token (401 Handling)
- **การตัดสินใจ**: เมื่อ Frontend ได้รับรหัสสถานะ 401 จาก API ระบบจะล้าง Token เก่าใน `localStorage` อัตโนมัติและสลับกลับไปยังหน้า Login ทันที
- **เหตุผล**: ป้องกันข้อผิดพลาด `invalid token` ค้างในเบราว์เซอร์เมื่อมีการเปลี่ยนหรือรีเซ็ตคีย์ในไฟล์คอนฟิก

### 6. การตรวจสอบโครงสร้างจริงเทียบกับเอกสาร (ก่อนเริ่มย้าย Angular)
- โครงสร้างโฟลเดอร์: backend อยู่ที่ `lifeplan/backend/` และ frontend เดิมอยู่ที่ `lifeplan/frontend/` (ไม่ใช่ `server/`)
- ตารางใน DB มี 5 ตาราง: `users`, `profiles`, `plans`, `plan_days`, `chat_messages` (ยังไม่มี `exercises` และ `user_memory`)
- ตาราง `profiles` จริงใช้ `name`, `goal`, `injuries` (ยังไม่มี `injuries_text`, `allergies_text`, `goal_text`, `consent_at`)
- ตาราง `plans` จริงใช้ `is_active` (ยังไม่มี `status`, `used_fallback`) และ `plan_days` เก็บเนื้อหาในคอลัมน์ `content` (JSON)
- Endpoints จริงมี 10 ตัว: `/health`, `/auth/{register,login}`, `/profile`, `/plan/{generate,current}`, `/plan/days/:dayNo`, `/plan/days/:dayNo/complete`, `/chat`, `/chat/history`
- สรุปแนวทาง: ยึด DB และ endpoint จริงเป็นหลัก การเปลี่ยนแปลงใน N1 จะทำแบบเพิ่มคอลัมน์ (ALTER ADD) ไม่ลบของเดิม
